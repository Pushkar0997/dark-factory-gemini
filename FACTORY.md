# Autonomous Software Factory Specification: Gemini Multi-Agent Factory

## 1. Factory Purpose

The Gemini Multi-Agent Factory is an autonomous, three-seat software engineering band designed to operate inside the [BAND Desktop](https://band.ai) collaboration platform. The factory receives an end-to-end software specification from a human operator and autonomously produces a fully tested, containerized HTTP service through structured inter-agent collaboration.

The factory is designed to be **problem-agnostic**: its mandates, coordination protocols, review mechanics, and progression logic contain zero assumptions about the target business domain. Any software challenge specifying containerized HTTP services with verifiable acceptance criteria can be delegated to this factory.

---

## 2. Design Philosophy

The factory operates on five foundational principles:

1. **Separation of Concerns**: Planning, implementation, and quality verification are partitioned across three distinct seats. No single seat is permitted to both author and unilaterally approve code.
2. **Strict Dark-Factory Autonomy**: Once a stage task is dispatched by the human operator, all intermediate decisions, problem solving, code generation, and test execution are handled autonomously by the band. The band never requests steering, clarifications, or intermediate approvals from the human.
3. **Self-Contained Handoffs**: Communication between seats must be complete and contextual. Seats do not rely on implicit room history or message IDs; each handoff carries the complete specification segment, constraints, repository location, and verification parameters.
4. **Independent Evidence-Based Verification**: The Reviewer never trusts claims or logs generated by the Builder. All checks, container builds, and test assertions are executed independently by the Reviewer on clean working checkouts.
5. **Continuous History Preservation**: Every progression step, successful review, or defect correction produces an atomic Git commit linked to the room discussion, creating an immutable audit trail of the factory's operation.

## 3. Seat Responsibilities

The factory configures three specialized seats:

```
[Human Operator]
       │
       ▼ (Single Stage Task Dispatch)
┌──────────────┐
│   Planner    │ ◄─── (Stage Completion / Blocker Escalation)
└──────┬───────┘
       │
       ▼ (Self-Contained Implementation Assignment)
┌──────────────┐
│   Builder    │ ◄─── (Defect Report / Revision Request)
└──────┬───────┘
       │
       ▼ (Committed Revision & Test Evidence)
┌──────────────┐
│   Reviewer   │ ────► (Approved Verdict / Verified Commit)
└──────────────┘
```

### 3.1 Planner (`@Planner`)
- **Role**: Software architect, project manager, and pipeline coordinator.
- **Responsibilities**:
  - Ingests the complete stage specification from the operator.
  - Decomposes the work into logical, ordered milestones.
  - Formulates self-contained implementation assignments for the Builder.
  - Monitors the verification cycle and manages defect remediation loops.
  - Formally advances the factory to subsequent stage directories upon Reviewer sign-off.
- **Invariants**:
  - Never writes application source code or patches files directly.
  - Never advances a stage without explicit, evidence-backed approval from the Reviewer.

### 3.2 Builder (`@Builder`)
- **Role**: Senior software engineer and containerization specialist.
- **Responsibilities**:
  - Ingests scoped assignments and architectural constraints from the Planner.
  - Implements clean, robust, and maintainable software within the designated stage directory.
  - Configures the service `Dockerfile` and `RUN.md` to ensure standard container execution.
  - Runs local unit and integration tests to verify functionality before handoff.
  - Commits changes to Git and reports the exact commit SHA and test results to the Reviewer.
  - Implements targeted fixes when the Reviewer reports defects.
- **Invariants**:
  - Never accepts its own work or declares a stage complete.
  - Never writes code outside the target stage directory.

### 3.3 Reviewer (`@Reviewer`)
- **Role**: Quality assurance lead, security auditor, and test engineer.
- **Responsibilities**:
  - Checks out the exact Git revision reported by the Builder.
  - Independently builds the container image and executes the test suites.
  - Validates compliance against the original specification, actively probing edge cases and concurrent safety.
  - Ensures backwards compatibility by verifying that all previous stage test suites continue to pass.
  - Formulates detailed defect reports with reproduction steps when regressions or failures occur.
  - Issues formal approval messages containing verification logs and commit references.
- **Invariants**:
  - Never edits or patches the code directly to make tests pass.
  - Never issues approval without independently executed verification runs.

## 4. Operational Protocols

### 4.1 Handoff Protocol
- Handoffs occur strictly via direct mentions using literal handles: `@Planner`, `@Builder`, and `@Reviewer`.
- Every delegated handoff from `@Planner` to `@Builder` must contain:
  1. The complete task description and acceptance criteria.
  2. The absolute path to the target repository and stage directory.
  3. All explicit constraints (port bindings, resource limits, network access rules).
  4. The required delivery artifacts (`Dockerfile`, `RUN.md`, source tree).
- If a specification exceeds message limits, it is transmitted in numbered segments with an explicit `[END OF TRANSMISSION]` marker.

### 4.2 Evidence & Review Protocol
- When `@Builder` completes implementation, it posts an evidence package containing:
  - The exact Git commit hash (`git rev-parse HEAD`).
  - The list of modified and created files.
  - The local test execution log and container build output.
- `@Reviewer` executes the verification independently:
  1. Inspects the diff between the previous stable revision and the new revision.
  2. Runs container build and test harness checks in an isolated environment.
  3. Verifies regression across earlier stage directories.
- If checks fail: `@Reviewer` replies with a **Defect Report** citing:
  - Failing test name or requirement clause.
  - Observed behavior vs. expected behavior.
  - Relevant logs and error traces.
- If checks pass: `@Reviewer` replies with a **Verification Approval** citing:
  - Verified commit hash.
  - Summary of passed test suites (current stage + regression).
  - Explicit sign-off for `@Planner` to proceed.

### 4.3 Failure & Retry Behavior
- When a defect is reported, `@Builder` is allocated a remediation turn to diagnose, fix, and commit.
- The factory permits up to 3 automated remediation cycles per milestone.
- If a defect cannot be resolved after successive attempts, `@Planner` evaluates whether a fallback architectural approach is feasible within the requirements.
- If a hard blocker is reached (e.g. system resource exhaustion or contradictory constraints), `@Planner` halts stage progression and documents the blocker, the attempted recoveries, and the evidence in the final room summary.

## 5. Stage Progression Protocol

The factory operates strictly sequentially across stages (`stage-1/` through `stage-4/`):

1. **Stage 1**: The factory starts with `stage-1/`. The Builder creates the base service, Docker container, and documentation.
2. **Promotion to Next Stage**:
   - Only when `stage-N/` has received formal approval from `@Reviewer`, `@Planner` authorizes advancing to `stage-(N+1)/`.
   - The Builder copies the verified `stage-N/` code into `stage-(N+1)/`.
   - The Builder verifies that the copied folder contains no `.git` subdirectory (preventing nested submodule links).
   - The Builder applies the incremental features required by stage `(N+1)` on top of the copied base.
3. **Cumulative Regression Audit**:
   - For `stage-(N+1)/`, the Reviewer executes test suites for Stage 1 through Stage `(N+1)`.
   - A stage is approved only if it passes all suites up to its own stage number without breaking earlier contracts.

## 6. Model & Harness Configuration

### 6.1 Harness Architecture
- The factory runs on the **Google ADK** adapter (`band-sdk[google-adk]`), connecting Python-based agent runtimes to the Band Desktop collaboration infrastructure via WebSocket and REST links.
- Each seat runs in its own process, loading credentials from a secure local configuration file and listening on room-specific message queues.

### 6.2 Model Strategy & Determinism
- **Default Models**:
  - Planner: `gemini-3.8-flash` (balanced reasoning and structured planning)
  - Builder: `gemini-3.8-flash` (code synthesis and fast generation)
  - Reviewer: `gemini-3.8-flash-lite` or `gemini-3.8-flash` (fast verification and code inspection)
- **Model Identity and Mandate Alignment**:
  - Official rules mandate that `mandates/<seat>.md` must accurately identify the exact `Harness` and `Model` that the seat executes.
  - Dynamic runtime fallbacks that silently swap model IDs without updating mandates can invalidate submission credentials.
  - The factory employs an **explicit model selection architecture**: models are centrally configured in `factory/config.py`. If a model fails to connect during startup, the factory logs a critical diagnostic rather than silently mutating the declared model identity during judged runs.

---

## 7. Security and Credentials Handling

- **Zero Credentials in Git**: Under no circumstances are API keys, bearer tokens, passwords, or session secrets committed to Git history or stored in repository files.
- **Local Secret Isolation**:
  - Real environment variables and API keys reside in `.env` or external environment stores that are excluded via `.gitignore`.
  - Configuration templates are committed as `.env.example` and `agent_config.yaml.example`.
  - The offline validation script scans all files for credential shapes prior to git commits.

## 8. Adaptation Guide: Using the Factory for Other Problems

To apply this factory to an unrelated software problem:
1. **Provide the Specification**: Formulate a written requirements specification defining the target service, HTTP endpoints, container contract, and acceptance tests.
2. **Configure Room Roster**: Create a room in Band Desktop with three seats matching the handles (`@Planner`, `@Builder`, `@Reviewer`).
3. **Dispatch Initial Task**: Paste the stage specification into the room addressing `@Planner`.
4. **Monitor Without Steering**: Allow the band to complete the decomposition, coding, and review loop autonomously.
5. **Collect Artifacts**: Download the completed service directories and export the session log as `room.json`.

---

## 9. Known Limitations & Tradeoffs

1. **Context Window Management**: Long multi-stage specifications can consume significant context tokens. The factory mitigates this by requiring the Planner to scope assignments into modular milestones.
2. **Tool Execution Latency**: Building container images and running browser-based end-to-end tests inside the Reviewer loop introduces turnaround latency. This tradeoff is accepted to ensure true independent verification rather than superficial static code analysis.
3. **Network Boundary**: During judging, runtime network access is completely blocked (`--mode isolated`). The Builder must ensure all dependencies, assets, and base packages are resolved during `docker build`.
